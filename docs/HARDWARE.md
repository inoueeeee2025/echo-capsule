# ハードウェア仕様

カセット型デバイス（筐体・基板・ファームウェア）の仕様と、アプリ側との接続契約。

> **今回のスコープ**
> スピーカーとマイクは間に合わないため**今回は搭載しない**。
> デバイスは「ボタン入力をアプリに送るコントローラ」として機能し、
> 録音・再生は挿入したスマホ側が担当する。

## 1. 構成

### 筐体（3Dプリント）

1つのデバイスとして以下を収める。

| 要素 | 状態 |
|---|---|
| スイッチ機構 | 試作2号機の反省を反映したプロトタイプ |
| スマホ挿入ギミック | あり |
| 基板 | ユニバーサル基板（ブレッドボードから移植予定） |
| 電池 | 9V 乾電池 + 降圧回路 |
| スピーカー | **今回はスキップ** |
| マイク | **今回はスキップ** |

**組み立て方針**：スイッチ機構のプロトタイプと、はせたくが作った `hontai` を組み合わせて1つのデバイスにする。

### 電子回路

| 項目 | 内容 |
|---|---|
| 電源 | 9V 乾電池を降圧。完全ワイヤレス動作 |
| 入力 | タクトスイッチ 3個（STOP / PLAY / REC） |

**現状**：ブレッドボード上に MVP 回路が完成。
**次**：ユニバーサル基板に移し、印刷した `hontai` に収まるサイズにする。

### ファームウェア

修正は必ずそこのファイルに入れてから実機に書き込む。手元にコピーを作って編集しない。

## 3. 通信プロトコル

### 方向

**デバイス → アプリの一方向のみ。** アプリからデバイスへは何も送らない。

### ボタン状態通知

```json
{
  "stop": true,
  "play": false,
  "rec": false
}
```

- `true` = 押されている / `false` = 押されていない
- **状態が変化したときのみ**送信（約50ms間隔のレート制限あり）
- 押しっぱなしの間も `true` が維持される（＝連続送信はされない。最後に送った状態が続いている）

### 接続時の初期送信

WebSocket 接続確立時に必ず一度、以下が送られる。

```json
{ "stop": false, "play": false, "rec": false }
```

### アプリ側の解釈

アプリは受け取った状態を前回値と比較し、**エッジ（押下 / 離す）を検出**して動作する。

| 場面 | REC | PLAY | STOP |
|---|---|---|---|
| rec 画面 | カセットモードへ移り、そのまま録音を始める | — | — |
| カセット・**録音中** | — | **止める**（押すと REC が上がるため）+ そのまま再生へ | **止める** |
| カセット・**確認待ち** | 押しながら録り直す | 聞く / 止める | **保管する** |
| カセット・通常 | 録音を始める | 再生 / 停止 | 次のカプセルへ |

**「REC が上がったら録音が止まる」**が基本。REC は固定式で他のボタンを押すと
機械的に上がるため、PLAY でも STOP でも `rec:false` が届いて停止する。

PLAY で止めた場合、その押下は停止に使われて消える。PLAY は固定式で
押し直せないため、止めたあとそのまま再生に入るようにしてある。

> **確認待ちで再生を途中で止める手段がない。**
> PLAY が固定式なので押し直せず、解除できるのは STOP だけ。
> その STOP は「保管する」なので、途中で止めると保存される。
> 気になる場合は割り当てを見直す。

実装箇所は `app/cassette.tsx` のボタン受け取り処理。

## 4. LED ステータス表示

| 状態 | LED |
|---|---|
| 電源投入直後 / Wi-Fi 未接続 | 青 点滅（500ms周期） |
| Wi-Fi に1台以上接続 | 青 点灯 |
| アプリと WebSocket 接続 | 緑 点灯 |
| 録音中 | 赤 点灯 |

優先度は上から「録音中 > WebSocket接続 > Wi-Fi接続 > 未接続」。

### ピン割り当て

| 用途 | ピン |
|---|---|
| STOP ボタン | 14（`INPUT_PULLUP`） |
| PLAY ボタン | 10（`INPUT_PULLUP`） |
| REC ボタン | 15（`INPUT_PULLUP`） |
| LED 緑 | 21 |
| LED 青 | 20 |
| LED 赤 | 18 |

ボタンは `INPUT_PULLUP` なので、**押下時が `LOW`**。

### 🔴 ボタンの機構（実装に強く影響する）

実物のカセットデッキと同じ機構になっている。**押している間だけ、ではない。**

| ボタン | 動き | 信号の出方 |
|---|---|---|
| REC | 押すと凹んで**固定される**。他のボタンを押すと解除 | 押した瞬間から `rec:true` が続く |
| PLAY | 同上 | `play:true` が続く |
| STOP | **固定されない**（押した瞬間だけ） | `stop:true` は一瞬 |

**STOP を押すと、REC と PLAY の固定が機械的に外れる。**
そのため停止操作では **`stop:true` と `rec:false` が同時に届く**。

この前提を外すと不具合になる。実際に次を踏んだ。

- 確認待ちのあいだ STOP を「保存」に割り当てていたため、
  録音中に STOP を押すと「録音の停止」と「保存」が同時に走り、
  後から終わった保存が勝って、録り直した音声が消えていた

**対策**：録音中はすべてに優先して「止める」だけを受け付け、そこで処理を打ち切る。
`app/cassette.tsx` のボタン受け取り処理を参照。

## 5. ファームウェアの検証結果

現行の Arduino コードを読んで検証した結果。**電気的・機械的な検証は含まない**（コードの論理のみ）。
ブレッドボード上で動作しているとのことなので、コンパイル・基本動作は問題ないという前提。

> **F-1 / F-2 / F-3 / F-4 / F-8 は修正済み。**
> 修正版は [`firmware/echo_capsule_controller/echo_capsule_controller.ino`](../firmware/echo_capsule_controller/echo_capsule_controller.ino)。
> **実機での書き込み・動作確認は未実施。** 以下は修正の根拠として残してある。

### 🔴 F-1. 50ms レート制限で、ボタンの状態変化が永久に失われる

**これが最も重大。** デモ中に「ボタンを押したのにアプリが反応しない」「録音が止まらない」を引き起こす。

```cpp
changed |= updateDebounce(bStop, now);   // ← ここで b.stable が新しい値に確定する
changed |= updateDebounce(bPlay, now);
changed |= updateDebounce(bRec, now);

if (changed && (now - lastSendMs) >= 50) {   // ← 50ms 経っていないと送信されない
```

`updateDebounce` は状態変化を検出すると、その場で `b.stable` を新しい値に**確定させて** `true` を返す。
しかし送信は `(now - lastSendMs) >= 50` で弾かれることがある。
弾かれた場合、次のループでは `b.stable == b.lastRead` なので `updateDebounce` は `false` を返し、
**その変化は二度と送信されない。**

**再現例**：REC を押す（送信、`lastSendMs` 更新）→ 10ms 後に PLAY を押す
→ デバウンス確定が 35ms 時点 → `35 - 0 = 35 < 50` → **PLAY の押下が永久に欠落**。

アプリ側は前回値との差分でエッジを取るため、
**「離した」が欠落すると、アプリは押されっぱなしだと思い続ける**（＝録音が止まらない）。

**修正案**：レート制限で送信を捨てるのではなく、保留して次に送る。

```cpp
bool pendingSend = false;   // グローバルに追加

void loop() {
  const uint32_t now = millis();

  if (updateDebounce(bStop, now)) pendingSend = true;
  if (updateDebounce(bPlay, now)) pendingSend = true;
  if (updateDebounce(bRec,  now)) pendingSend = true;

  // 録音フラグは毎ループ更新する（F-3 の修正も兼ねる）
  recording = (bRec.stable == LOW);

  if (pendingSend && (now - lastSendMs) >= 50) {
    lastSendMs = now;
    pendingSend = false;          // ← 送れたときだけ降ろす

    if (ws.count() > 0) {
      char msg[96];
      snprintf(msg, sizeof(msg),
        "{\"stop\":%s,\"play\":%s,\"rec\":%s}",
        (bStop.stable == LOW) ? "true" : "false",
        (bPlay.stable == LOW) ? "true" : "false",
        (bRec.stable  == LOW) ? "true" : "false");
      ws.textAll(msg);
      Serial.println(msg);
    }
  }
  // …LED制御…
}
```

送るのは常に「3ボタンの現在の確定状態」なので、
保留中に別の変化が起きても最新状態が1回で送られる。取りこぼしがなくなる。

### 🔴 F-2. `ws.cleanupClients()` が呼ばれていない

ESPAsyncWebServer / AsyncWebSocket は、切断されたクライアントを解放するために
**`loop()` 内で定期的に `ws.cleanupClients()` を呼ぶ必要がある**。現行コードには無い。

これが問題になるのは、**アプリ側が上限なしで無限に再接続を試みる**ため
（`src/hardware/ws.ts:62-71`、最大5秒間隔で永久にリトライ）。
接続と切断を繰り返すたびに解放されないクライアントが溜まり、
**長時間のデモ中にメモリを食い潰して不安定になる／固まる**可能性がある。

**修正案**：`loop()` の先頭あたりに追加。

```cpp
void loop() {
  const uint32_t now = millis();

  static uint32_t lastCleanupMs = 0;
  if (now - lastCleanupMs >= 1000) {
    lastCleanupMs = now;
    ws.cleanupClients();
  }
  // …
```

> ⚠️ 現行の LED 制御は各分岐で `return` して `loop()` を抜けるため、
> `cleanupClients()` を LED 制御より**後ろ**に書くと、録音中や接続中に呼ばれなくなる。
> **必ず `loop()` の先頭側に置くこと。**

### 🟠 F-3. 録音中でも赤 LED が点かないことがある

`recording` の更新が、送信ブロックの中（`if (changed && …)` かつ `if (ws.count() > 0)` の内側）にある。

```cpp
if (changed && (now - lastSendMs) >= 50) {
    if (ws.count() > 0) {
      recording = (bRec.stable == LOW);   // ← ここでしか更新されない
```

つまり：

- **WebSocket が未接続だと `recording` が一度も更新されない** → REC を押しても赤くならない
- F-1 でレート制限に弾かれた場合も更新されない → 状態がずれたまま残る

**修正**：F-1 の修正案のとおり、`recording = (bRec.stable == LOW);` を毎ループ実行する位置に移す。

### 🟠 F-4. 接続状態の管理が二重になっている

`wsClients`（イベントで手動カウント）と `ws.count()`（ライブラリの実数）の2つが併存し、
**LED 制御は `wsClients`、送信判定は `ws.count()`** と使い分けられている。

`WS_EVT_DISCONNECT` は、Wi-Fi が突然切れた場合など**必ずしも発火しない**。
その場合 `wsClients` が減らず、**実際には誰も繋がっていないのに緑 LED が点灯し続ける**。

**修正案**：`wsClients` を廃止し、LED 判定も `ws.count() > 0` に統一する。
`cleanupClients()`（F-2）を入れれば、少なくとも「切断済みなのに残っている」状態は解消される。
ただし完全な正確さには F-8 の ping も必要。

### 🟠 F-8. キープアライブ（ping）が無いため、切断を検知できない

`ws.pingAll()` を呼んでいないため、TCP の keepalive 任せになっている。

スマホが AP から**黙って離れた**場合（電波が届かない・OS が別回線に切り替えた）、
FIN が飛ばないので**サーバー側は接続が生きていると思い続ける**。

- `ws.count()` が減らないため、**繋がっていないのに緑 LED が点灯し続ける**
- F-4 を修正して `ws.count()` に統一しても、この経路では同じ症状が残る

デモ中に「緑なのに反応しない」という一番分かりにくい状態を作るので、対処しておく価値がある。

**修正案**：定期的に ping を送る。応答しないクライアントは
`cleanupClients()` 側で回収され、`ws.count()` が正しく減る。

```cpp
static uint32_t lastPingMs = 0;
if (now - lastPingMs >= 3000) {
  lastPingMs = now;
  ws.pingAll();
}
```

F-2 の `cleanupClients()` と同じく、**LED 制御の `return` より前**に置くこと。

### 🟡 F-5. 接続時の初期送信が実際のボタン状態を反映しない

```cpp
client->text("{\"stop\":false,\"play\":false,\"rec\":false}");
```

接続の瞬間にボタンが物理的に押されていても `false` を送る。
アプリ側の前回値も全 `false` 始まりなので**通常は整合するが**、
「ボタンを押しながら接続 → 離す」の順だと、アプリは押下も解放も観測できない。

**修正案**：実状態を送る。

```cpp
char msg[96];
snprintf(msg, sizeof(msg),
  "{\"stop\":%s,\"play\":%s,\"rec\":%s}",
  (bStop.stable == LOW) ? "true" : "false",
  (bPlay.stable == LOW) ? "true" : "false",
  (bRec.stable  == LOW) ? "true" : "false");
client->text(msg);
```

ただしこの場合、アプリ側の `prevHardwareStateRef` は全 `false` 始まりなので、
接続直後に「押されている」を受け取ると**押下エッジとして扱われる**点に注意。
デモ運用上は「ボタンを押していない状態で接続する」で回避できる。

**逆方向の注意（現行仕様のまま残る挙動）**：
アプリは切断されると無限に再接続する（`src/hardware/ws.ts:62-71`）。
**REC を押しっぱなしのまま Wi-Fi が一瞬切れて再接続**すると、
初期送信の `rec:false` が `recUp` エッジになり、**録音がその場で停止・保存される**。
今回は「REC を離したら保存」なので実害は小さいが、
長押し中の再接続で意図せず保存される可能性は認識しておくこと。

### 🟡 F-6. アプリ → デバイスの通信経路が存在しない

「録音できない時はインジケーターを赤にしないように、アプリからこいつに向けて通信してもいい」
というアイデアについて、**現状は両側とも未実装**。

- **ファーム側**：`onWsEvent` が `WS_EVT_CONNECT` と `WS_EVT_DISCONNECT` しか処理していない。
  `WS_EVT_DATA` のハンドラが無いため、アプリが何か送っても無視される
- **アプリ側**：`src/hardware/ws.ts` に送信メソッドが**1つも無い**（受信専用のクラス）

この課題は実在する。現在の赤 LED は「RECボタンが物理的に押されているか」だけで決まるため、
**アプリ側の録音が失敗していても赤く光る**（マイク権限拒否、`docs/TASKS.md` B-2 の競合状態など）。
「光っているのに録れていない」が起きうる。

実装するなら両側に追加が必要（ファーム側の `WS_EVT_DATA` ハンドラ + アプリ側の `send()`）。
**発表まで1週間なら、これは見送るのが妥当。**

### 🟡 F-7. その他（優先度低）

- `volatile uint32_t wsClients` は非同期タスクから更新されるが、`volatile` だけでは不可分性を保証しない。F-4 で廃止すれば解消する
- `ws.textAll()` を `loop()` から呼んでいる。クライアントの受信が遅いと内部キューが溜まるが、50ms間隔・48バイト程度なので実用上は問題にならない見込み
- `snprintf` のバッファ96バイトに対し実メッセージは最大48バイト程度。余裕あり
- ピン番号（14/10/15、21/20/18）とインクルード `<RPAsyncTCP.h>` から RP2040 系（Pico W）と推測されるが、実機で動作しているとのことなので指摘なし

## 7. デモ当日のリスク

ネットワーク構成に起因する、コードでは解決できないリスク。

### 🔴 スマホが AP から勝手に離れる

デバイスの AP は**インターネットに繋がっていない**ため、OS が自動的に別の回線へ切り替えることがある。

- **iOS**：「インターネット未接続」と表示され、モバイル通信を優先する。
  ローカルIPへのアクセス自体は維持されるが、**Wi-Fi Assist が有効だと切断されることがある**
- **Android**：「このネットワークはインターネットに接続していません」の確認が出る。
  **「このまま接続」を選ばないと自動的に切断される**

**対策**：デモ前に一度接続して、確認ダイアログに「このまま接続」で答えておく。
iOS は設定 → モバイル通信 → Wi-Fi アシストをオフにしておく。

### 🔴 iOS のローカルネットワーク許可

iOS 14 以降、ローカルネットワーク上の機器への接続には**ユーザーの許可**が必要。
初回接続時にダイアログが出る。`app.json` に `NSLocalNetworkUsageDescription` が無いと
説明文が空になるか、そもそも許可を求められない。

→ `docs/TASKS.md` の **A-2** で対応する。

### 🟠 Metro との切断（開発ビルドで運用する場合）

Expo Go / 開発ビルドで動かす場合、**デバイスの AP に繋ぎ替えると Metro サーバーに到達できなくなる**。
未ロードの画面やアセットを開こうとすると失敗する。

`app/record/rec.tsx:230-248` にプリロード処理があり、この問題への対策として
cassette / kaihuu / kaihuu-text の画面コードと22個のアセット
（`CASSETTE_PRELOAD_ASSETS` 7個 + `MOBILE_MODE_PRELOAD_ASSETS` 15個）を起動時に先読みしている。

### 🟠 電池残量

9V 乾電池での完全ワイヤレス動作。Wi-Fi AP + WebSocket サーバーは消費が大きい。
**予備の電池を用意し、リハーサル時に連続動作時間を実測しておくこと。**
